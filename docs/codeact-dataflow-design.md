# CodeAct 数据流优化设计

状态：方案记录，主分支执行协议与函数接口未变。后续已在独立实验分支完成候选实现和真实模型评测，结论暂不上线，见[候选评测与返回值核对](codeact-dataflow-evaluation.md)。设计依据为 [Sol 小样本对测](pimoon-opi-sol-benchmark.md)。

## 目标

让确定性的数据流留在 Python，仅在需要模型理解、决策或向用户报告时跨回模型。优化实际总 token 和任务成功率，不以工具调用数、代码块数或估算 token 单独作为成功指标。

不是让所有任务变成一块，也不是给发票、JSON 或批量编辑增加专用工具、示例或硬编码规则。

## 根因：程序接口仍混用了展示协议

现有 `native-instructions.ts` 已要求已知步骤一次完成、仅返回决策相关发现。继续叠加同义提示，不能解决接口与该目标不一致的问题。

| 边界 | 当前行为 | 对通用编排的影响 |
| --- | --- | --- |
| `read` | 文本的 `structuredContent` 仍是 `<read>` 展示文本 | Python 需理解展示协议，不能直接解析文件正文 |
| `ls` | 没有输出 schema，返回格式化目录文本 | Python 需解析目录展示，或改走另一套原生文件访问 |
| `find/grep` | 已有结构化选中结果、截断标志 | 可直接用于路径筛选和后续操作，是可复用的已有路径 |
| `native_read` | 返回原文，路径检查独立；不建立文件工具编辑观测 | 读取计算与读取修改之间存在容易误用的语义分叉 |
| 失败 | 文件工具底层已有错误码，展示后桥接常只传字符串 | 代码依赖 `ENOENT` 等文案判断，或交回模型处理 |
| 执行输出 | 显式 print 和末尾表达式可输出大量数据，未赋值调用另有短预览 | 数据虽然驻留 Python，仍容易完整回灌模型 |

相关实现：`file-tools/pi/adapters/read.ts`、`adapters/ls.ts`、`read-output.ts`、`search-output.ts`、`shared/result.ts`、`pimoon/runtime.mjs`、`worker.py`、`execution.py`、`feedback.py`。

## 设计原则：数据、证据、展示分开

```text
宿主函数
  -> 稳定的程序数据 -> Python 继续读取/计算/校验/操作
  -> 人可读展示    -> GUI/审计
Python 的显式结果与异常
  -> 模型所需证据  -> 判断/解释/下一步计划
```

沿用 SDK 已有 `structuredContent` 与 `content/details`，不引入第二个编排器、模型摘要器、结果仓库或通用查询 DSL。展示与程序数据来自同一次操作，不能为不同输出再读一次文件或重放副作用。

### 1. 先补齐可计算的函数结果

优先补 `read` 和 `ls`，不先改所有插件：

- 文本 `read` 的程序结果应保留原始读取片段及范围、完整性与继续读取信息，不包含 XML 展示标签或代码结构提示。GUI 仍可使用现有可读呈现。
- 完整读取和分段读取必须可区分；不把多段拼成一份“完整正文”，不把截断 JSON 当作完整 JSON。编码、BOM、换行的具体语义需在实现前固定并测试，不把现有行视图冒充逐字节原文。
- 文件版本与编辑观测仍由原文件工具建立和复验，不把内部版本令牌、完整扫描诊断等全部暴露进目录 schema。
- `ls` 返回路径/条目类型、截断与必要的范围错误。优先复用现有底层结果的最小投影，不让 Python 从展示字符串重新识别文件名。
- `find/grep` 延用现有结构化选中证据，检查 `truncated/scope_errors` 后才能声称处理了全部匹配。
- 图片和 PDF 保留类型分支；不把二进制或 Base64 自动灌入 Python 文本和模型文本。
- 第三方无输出 schema 的函数明确保持文本语义，不猜 JSON、不剥 XML、不自动探测格式。

不新增 `read_json/read_csv/summarize_invoices`：格式处理属于标准库或项目函数，工具只负责合法、可验证的 I/O。

`native_read` 暂不作为默认解决方案，也不偷偷将其升级为“已经 read 过”。待上述受观测读取可满足数据流程后，再单独决定其必要性；若删除需同步目录、文档和测试，不保留两个声称等价的接口。

### 2. 保留机器可处理的失败

- 单项调用维持失败即停止依赖步骤的行为，但把稳定错误码、必要路径和简短消息带到 Python；可用明确的工具异常承载，而非在业务代码中匹配自然语言。
- 批次仍按输入顺序返回逐项成功/失败，失败项保留相同错误码。不能因 `structuredContent` 存在就将宿主 `isError` 包装成成功；`process_run(check=False)` 等显式返回的业务状态仍按其契约检查，不能混淆执行成功与业务成功。
- 缺失可选文件等预期分支可在 Python 根据明确错误码继续；拒绝权限、取消、观测失效等不得转为“跳过所有错误”。必需输入失败必须阻止依赖写入。
- 模型反馈中给出简短、可定位的失败证据；完整调用记录留在审计。去重同一错误的展示不等于抹除部分失败或自动标为已处理，未经可靠确认不得静默隐藏错误。

这使文件扫描、批量校验、HTTP/进程状态检查和构建产物处理都更容易留在程序内，不依赖某一种任务。

### 3. 用“是否需要新判断”决定块边界

通用决策规则应替换现有同义规则，而不是叠加：

- 后续步骤可由明确规则、返回数据和状态分支决定：继续同一块，包括顺序依赖步骤；独立 I/O 才 batch。
- 新内容需要模型语义判断、用户选择或证据不足：返回最小充分证据后停止。
- 读取、计算、验证与写入是依赖关系，不是天然的模型轮次边界。
- 不用代码臆测业务意图；修改未知源码、比较设计方案等需要模型理解时，回传相关片段是正确行为。
- 内部权限审批继续暂停原调用；不为少一轮取消审批、重新执行代码或扩大写入范围。

典型边界对比：

| 数据流 | 合理行为 |
| --- | --- |
| 已知格式的数据过滤、统计、转换 | Python 内处理，返回统计与产物信息 |
| 已知条件的多文件修改 | 按文件读取观测、计算差异、精确修改、验证；返回实际变化 |
| 批量状态检查或测试结果统计 | 程序处理成功项；只返回必要的失败证据与完整性状态 |
| 阅读未知实现后决定怎么改 | 返回相关源码，保留模型判断边界，不强行合并 |

### 4. 输出是证据出口，不是数据总线

- 中间数据赋值留在命名变量；最后表达式返回结果、变化、检查结果或少量样本。需要完整数据时再明确输出，而非默认打印整个 batch。
- 复用现有短预览、`observe`、`_` 和 `_results`，不再新增结果句柄/表格 API。已有能力的可发现性和保留期限要准确，不承诺重启后仍存在。
- 不擅自重写用户 `print`，不把“输出少”视为“计算正确”。需要压缩默认展示时必须是明确的预览：说明截断、保留位置与失效条件；完整值不因展示裁剪丢失。
- 错误、截断、部分结果、已完成写入与取消状态必须可见。禁止用一个无条件 `ok` 摘要掩盖缺失数据，也不自动重跑产生副作用的代码。
- 不自动让另一个模型总结结果；它会增加请求、延迟和信息损失。

### 5. 固定说明按能力收敛

新接口不能以更长的工具目录抵消收益：

- 常驻只保留执行边界、状态、基本展示和安全约束。
- `process_run/http/webfetch` 等说明仅在相应能力启用时出现；每条规则只放一层。
- 参数和返回值含义来自 schema，范围/截断/失败等事实由结果表达；不同时在工具目录、系统策略和执行规则重复描述。
- 保留一个 `execute`，不为这个需求引入运行时工具搜索或复杂分级加载。
- 原始文件/网页 payload 的 Unicode 不改写；自生成的预览标记继续用紧凑 ASCII。

## 实施顺序

1. **程序结果契约**：先完成 read/ls 的最小结构化输出和失败语义，接通现有桥接。同步更新受影响调用者，不保留解析旧展示字符串的兼容层。
2. **执行策略**：基于可直接使用的数据契约，精简并重排当前规则；按已启用能力生成必要说明。先不要同时修改输出上限与持久化机制。
3. **输出默认值**：根据新样本再判断是否需要调整默认预览。先验证减少不必要回传，再决定展示预算；不先堆自动截断机制。

每一步单独检查实际输入基线，避免“少了历史、多了常驻说明”的倒退。它们是同一个数据流设计的分阶段落地，不是逐个 benchmark 添加例外。

## 验证与验收

### 离线真实流程优先

- 完整/分段/截断文本、Unicode、BOM、CRLF、无末尾换行，以及正文含 `<read>` 等字符串；程序处理不依赖展示标签，也不错误拼接片段。
- 真正经过文件工具 read 建立观测后修改；外部并发改写触发失效，不因新结果类型绕过守卫。
- 目录名含空格/Unicode，多层筛选，截断和范围失败必须被识别。
- 可选缺失与必需缺失分别处理；权限拒绝、取消、批次部分失败不诱导继续依赖写入，不重放已完成写入。
- 用同样的程序数据结果覆盖至少数据转换、条件文件修改、状态检查三类流程；不只测试发票 fixture。
- GUI/审计展示与 Python 数据来自同一操作；图片不重复文本化，完整数据驻留与预览保留语义正确。

低层测试可验证接口、取消、守卫与数据完整性；模拟模型按既定代码执行通过，不证明真实模型会自然合并步骤。

### 少量真实模型对照

继续使用 Sol、相同思考级别与现有三项任务，交替顺序，各边至少三次。若前三项稳定，再加一个必须回传源码供模型判断的任务，检查是否发生过度合并。复测须明确使用订阅并在隔离目录运行，不在本设计阶段自动发请求。

验收同时观察：

- 文件结果正确、成功率、部分失败与恢复行为；
- 实际 usage（非缓存/缓存/输出/总量）、模型请求轮数、墙钟与工具区间并集；
- 首轮固定输入、每项历史输入增长、模型实际接收的工具文本，而非内部函数产生了多少数据；
- 规则和目录增加的固定成本，是否被跨任务的真实收益抵消。

目标不是保证所有任务一轮完成，也不预设节省比例。只有准确性不退化、实际 token 或耗时在多类任务中稳定改善，才认为整体优化有效。
