# 工具执行系统测试与优化

2026-11-03，Windows x64，Node 24.18.0、Python 3.12.9。

2026-11-04 的真实 Codex / Terra 对测及当前结论见 [Terra 真实工具调用对测](terra-tool-comparison.md)。下文仅保留历史离线数据。

> 本文性能数据对应历史的“直调 + 可选 CodeAct”方案，不代表当前架构。现已收敛为 CodeAct 唯一执行入口，见 README 与 VALIDATION.md。基准脚本也已改为让 pimoon 全部操作经过 CodeAct，不能将新结果冒充原来的直接文件工具对测。

## 结论

- 单次文件操作已与 o-pi 同源基线处于同一量级，不需要通过 Python，也没有增加模型往返。
- 应保留“简单操作直调，批量任务 CodeAct”的分工。CodeAct 现已随应用初始化当前工作区会话时后台预热；不需要增加模型可见模式、提示词或输入 token。
- 批量独立读取的明显收益来自并发和只返回决策需要的结果，不来自替换 SDK 或削弱安全检查。

## 测试边界

检查了 `<o-pi 安装目录>/resources/app.asar`，安装版为 o-pi 1.4.0；其文件工具描述与仓库实现一致。性能基线使用 `../o-pi` 的文件工具源码：文件工具扩展与 pimoon 相同，工具目录仅会话观察状态的品牌标识有差异。

基准通过 esbuild 分别打包两个仓库的工具扩展，使用同一 Pi SDK、本地固定响应 HTTP 服务及现有桌面构建的解析 worker/资源。真实执行文件工具、宿主路径检查、Python/Rust 桥接和 pimoon 遥测。不启动 Electron，不调用付费模型。

这不是安装版 Electron 端到端对测；不包含模型思考、远程网络、GUI 投影和渲染时间，也未加载完整宿主的其他扩展。不能据此宣称整段对话一定快于当前 o-pi 环境。固定模型响应不能证明真实模型的工具选择正确率。

每种操作执行 10 次：单独列出首次调用，其余 9 次统计中位数和 P95。文件系统缓存为热；首次调用不是应用启动，CodeAct 可能已在后台预热完成。基线先运行，pimoon 后运行，顺序与系统抖动会影响小幅差异，因此只判断同一量级，不把数毫秒差距当成稳定领先。

## 最近两轮成对对测结果

下表为两轮各自热调用中位数的范围，单位 ms：

| 操作 | o-pi 源码基线 | pimoon |
| --- | ---: | ---: |
| ls：128 个目录项 | 17.4–17.9 | 18.6–18.7 |
| read：小文本 | 7.5 | 7.7–7.9 |
| find：128 个路径中定位文件 | 11.3–12.0 | 11.4–11.6 |
| grep：限定一个文本文件 | 9.2–9.6 | 9.6–10.2 |
| grep：128 个 TS 文件 | 37.6–38.9 | 38.8–40.9 |
| write：整个小文件 | 10.2–11.6 | 11.1–11.6 |
| edit：精确替换 | 10.1–11.3 | 11.0–11.9 |

CodeAct：

- 后台启动 Python 约 194–237 ms；预热完成后的首次简单执行约 2.9 ms，后续约 0.9–1.2 ms。上轮按需启动时首次约 215–367 ms。启动成本是前移并重叠，不是消失；若应用刚打开即调用，仍需等待剩余初始化时间。
- 单次嵌套 read 约 8.7–8.9 ms；直接 read 约 7.7–7.9 ms，仍应优先直调。
- 8 个不同文本文件，`batch("read", jobs, limit=6)` 约 23.4–23.7 ms；Python 内顺序读取约 68.1–72.6 ms。上轮分别约 34–39 ms 和 96–97 ms，但本轮 o-pi 基线也变快，不能将跨轮全部差值归因于本次修改。
- 批处理只返回数量的结果不适合需要查看全文的任务；测试中的摘要是主动投影，不能据此认为真实代码任务总是只需几个输出 token。

## 已实施的优化

1. **补齐可执行的批处理说明，不增加工具入口。** 声明既有 `batch(name, jobs, limit=6)`、只读工具范围、并发上限和有序返回格式。重写后 CodeAct description 从约 145 降至 140 token。基准中 7 个工具的声明在相同序列化口径下从 1012 降至 1007 token；其中只有文件工具时为 822 token。
2. **压缩 CodeAct 结果包装。** 正常结果使用 `ok` 加原始输出，失败使用 `error` 加原始错误；删除重复的完成句、耗时句和 Output 标签。耗时仍在结构化指标与 GUI 中。相同短输出从 15 降至 4 token，嵌套 read 从 223 降至 212 token；错误、部分失败、输出截断和原文均保留。
3. **遥测后台批量写盘。** 事件只生成元数据并入队，默认 25 ms 合并后通过 Node 异步文件 I/O 串行写盘；工具和模型请求不等待写盘。队列含在途批次最多 1 MiB，进程日志最多 64 MiB；超限或失败标记不完整并提示，已接收记录仍尝试排空。会话关闭和桌面后端正常退出显式排空；自然退出也收尾，强杀或崩溃仍可能丢尾部。当前累计入队时间约 26.3–26.7 ms，后台 I/O 等待累计约 392–433 ms，二者独立统计，后者不能加到工具延迟里。入队计时不含调用前的指纹计算；请求绑定所需校验仍同步执行，不宣称遥测零 CPU 成本。工具遥测区间在开始记录入队之后、结束指纹生成之前采集；SDK 基准仍保留真实墙钟时延，不通过减法美化结果。上轮同步句柄版本累计约 92–106 ms，更早逐条开关文件约 333 ms，均为历史记录口径，不与异步 I/O 等待直接比较。
4. **统一 GUI 与执行边界的工具开放集合。** 清除仍把直接文件工具隐藏的旧投影规则；GUI 与模型声明保持一致，避免误导用户以为文件操作必须走 CodeAct。
5. **修正测试夹具。** 项目配置使用 `.pimoon/configs`；取消测试等待写入正文可见，而非仅等待文件创建，避免将未完成的缓冲写入误判为已完成写入。
6. **启动时预热当前会话。** SDK 的 session_start 后台发送 INIT，准备解释器和工具代理，不执行用户代码或请求模型。只为已初始化且启用 CodeAct 的会话创建一个运行时，不扫描历史会话预启动进程；GUI 原有资源回收和 session_shutdown 负责释放。10 秒初始化上限、失败后按需重建、提前幂等关闭均受控。等待预热时取消通过关闭管道让监督器释放 Python，不强杀仍持有子进程的 Rust 父进程。仅初始化不算已有 Python 变量，恢复历史会话仍提示内存为空；不同会话不共享变量。

所有 token 数都是通用 o200k_base 本地估算，不是供应商计费数据。未缩短原始文件 payload，未增加模型回合，未关闭审批、路径检查、取消或错误报告。

## 功能回归

- Vitest：26 个文件，371 项通过，6 项按原有 Windows 条件跳过（权限/符号链接场景）。
- 真实 Python/Rust 执行器：15 项通过。
- 全项目 TypeScript 类型检查通过。
- 新增 SDK 批处理集成测试：一次工具回合完成 8 次读取；另含不存在文件和越界路径，按序返回且保留两项失败。共 2 次模型请求：一次选择工具，一次读取结果并作答；不是每个子工具一次模型请求。
- 新增执行器测试：批处理并发受限、按序返回、部分失败不停止其他读取，简短包装不丢正文和异常。
- 直接 read/edit 测试确认预热阶段没有模型请求，文件工具不经过 Python，并验证 GUI 使用的过滤规则与真实模型声明一致。
- SDK 集成测试确认首次 CodeAct 复用预热 PID，重启同一历史会话后不会误认变量已恢复。执行器测试覆盖预热无代码执行、会话隔离、初始化失败、提前关闭、等待预热时取消，以及 Python 意外退出后的恢复。
- 遥测测试覆盖写盘挂起时生产者仍可入队、并发排空顺序、总量/队列上限、写入失败和隐私；基准检查排空后事件序号连续。
- 没有运行抢焦点的桌面测试或付费模型烟测；没有重建桌面包，源码优化尚未进入现有 `dist/pimoon`。后续已安装官方 Bun 1.4.4 至 `<Bun 安装目录>`，官方 npm SHA-512 校验、构建帮助及 `bun run typecheck` 均通过，构建环境阻塞已解除。

## 后续优先级

- 保持简单调用无需选模式；让模型直接使用现有文件工具。
- 已知范围时限定 path/glob，避免把几十毫秒的小查询扩大成全库扫描；不新增一套需要模型判断的“快速 grep”接口。
- 需要进一步压缩体感延迟时，先在隔离环境测完整宿主和真实模型的请求数、首事件时间、误用重试及有效输出 token，再决定是否值得继续优化宿主启动或搜索算法。
- 不预启动全部历史会话，不取消读前校验，不缓存未经验证的文件结果，不自动压缩全部文件正文；这些会增加资源占用、错误修复调用或认知成本。
