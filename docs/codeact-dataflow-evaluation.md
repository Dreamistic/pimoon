# CodeAct 数据流候选评测

2026-11-05。结论：**保留实验分支，暂不上线。** 数据接口和多文件编排有明确改善，但简单任务退化、模型仍偶尔回传中间数据，尚不足以证明整体稳定获益。

## 隔离与版本

- 基线：`21ab432` 的干净工作树，不包含主工作树已有的遥测、执行统计等未提交改动。
- 候选：`experiment/codeact-dataflow`，最终提交 `00950d3`；首版提交 `61c8ddb`，之后修正执行规则、去除返回类型重复说明并紧凑输出 JSON。
- 两个工作树分别在 `.tmp/tests/codeact-dataflow-baseline/` 与 `.tmp/tests/codeact-dataflow-candidate/`。候选代码没有合并到 main，也没有覆盖现有桌面资源、构建桌面交付包或推送。
- 同一只读借用依赖、同一 Rust 执行器；每个变体使用各自的 Python 源码副本。应用配置、HOME 和临时文件均隔离。
- OAuth 只读，经 stdin 传入，不写入测试凭据文件、不刷新。所有运行 manifest 均校验源凭据未变化。
- 模型 `openai-codex/gpt-6.1-sol`，thinking `low`，SSE；重试和自动压缩关闭。

这里比较的是新旧 pimoon 的代理工具回路，不是桌面 GUI，也不是再次拿 o-pi 作对照。后续若合并主工作树已有改动，需要重新验证组合版本，不能把本次结果当作该组合版本的测量。

## 候选改动

1. `read/ls` 的 `structuredContent` 提供程序数据，`content/details` 保留人可读展示和审计；来自同一次操作，不通过解析展示标签或第二次读取得到。
2. 文本分段保留原换行，UTF-8 BOM 不进入正文；`full_file` 区分完整文件，`more` 给出未读的请求范围，不拼接非连续片段冒充完整文件。
3. 文件错误的稳定 code/path 进入 `ToolError` 和 batch 失败项；即使存在结构化载荷，宿主 `isError` 也不再被误包装成成功。
4. 缺失目标经过原始路径和真实祖先保护检查后，交回文件工具产生明确缺失错误；原生 `native_read` 仍要求目标存在。保护路径及其链接后代未放开。
5. 执行规则强调确定性步骤留在 Python，按已启用能力生成说明；明确 batch 的可用函数和全局辅助函数边界。输出 schema 的类型仅列一次；末尾表达式 JSON 改为紧凑序列化，未改写 print，也未加入自动摘要模型。

## 返回值核对

### 文本读取

```json
{
  "type": "text",
  "path": "input.json",
  "segments": [{"start_line": 1, "end_line": 1, "text": "{\"value\":42}"}],
  "full_file": true
}
```

- 程序从 `segments[].text` 取得正文，不剥 `<read>` 或结构导航标签。
- 仅 `full_file=true` 才能假设读到了整个文件。指定部分范围时可以 `full_file=false` 且没有 `more`；这是请求范围完整，不是整个文件完整。
- 预算截断会给出 `more`；非连续区间保持分段。空文件为一个空文本片段，仍可 `full_file=true`。
- 图片/PDF 维持原类型分支，图片内容块原样传递，不因这次修改自动转成文本或重复 Base64。
- 读取仍建立编辑版本观测；未读取、外部并发修改及权限错误仍会阻止依赖修改。

### 目录与失败

```json
{"path":"inputs","entries":[{"path":"inputs/a.json","type":"file"}],"truncated":false}
```

目录截断时 `truncated=true`，`next` 给出缩小范围的提示，不承诺可对整个目录完成汇总。

```json
{"ok":false,"error":{"code":"FILE_NOT_FOUND","message":"File does not exist.","path":"inputs/missing.json"}}
```

这是 batch 的逐项失败；单项调用抛 `ToolError`，可检查 `.code/.path`。未知插件错误使用 `TOOL_ERROR`，不猜测错误字符串。错误即使被代码捕获，执行反馈仍保留 `tool_failures`；根结果 `ok` 只表示 Python 块完成，不等于任务正确或全部内部操作成功。

这是破坏性的读取返回类型变化，旧脚本的 `json.loads(read(...))`、字符串成员判断等需要迁移。候选中已修改受影响测试，未加入解析旧字符串的兼容层；现有桌面版接口未改变。

## 实际模型结果

只对**任务成功且 usage 完整**的运行取中位数，失败尝试保留在数据中，不把未知 token 当零。每个任务的各列分别取中位数，不把这些中位数拼成一条真实运行。

最终候选与基线的数据来自不同批次；前期比较交替顺序，最终候选批次在后。网络与服务端缓存未受控，因此墙钟时间只能作为观察，不能证明实现的因果加速或减速。

工具 token 是可见载荷的 `o200k_base` 估算，包含各轮重复工具定义、历史调用/结果和生成调用，不代替供应商实际总量。工具耗时不重复累加内部调用和并行区间。

最终候选的实际总 token 样本：

- 定位修改：`5199, 7049, 6943`；有一次降到三轮，但两次仍四轮，不能只挑最好的一次。
- 汇总：完整成功 `6455, 6645`；另有两次 `fetch failed`，总 token 不完整，不参加中位数。一次失败发生在文件写完后的最终回复；离线校验产物通过，但仍不算完整流程成功。
- 批量编辑：`6663, 6242, 6631`，三次均三轮，无根执行错误；相比基线的读前编辑拒绝后恢复，表现更稳定。

纳入最终比较的基线为 10 次尝试、9 次完整成功；最终候选为 10 次尝试、8 次完整成功。不能据此把服务/传输层失败率差异归因于接口，也不能声称候选全流程 100% 成功。

## 为什么暂不上线

1. **简单任务退化。** 最终首轮实际输入比基线约多 28–29 token；新返回结构和契约仍有固定成本。定位任务常未省轮数，回传结构也更长，最终中位数增加。
2. **中间回传未根治。** 汇总完整样本的根工具返回文本估算中位数从 914 降至 365.5，多文件编辑从 1,054 降至 328；但模型仍会把部分记录返回后再算，不是稳定的一块完成。
3. **接口能力不等于策略收益。** 第一版三次批量编辑分别消耗 `16114, 15859, 12569`，还不如基线；精简规则造成 batch edit 误用。后续明确允许的 batch 名称和全局辅助函数边界后才改善。失败版本未从记录中删除。
4. **汇总样本与耗时仍不充分。** 最终汇总只有两个完整 usage 样本，墙钟中位数反而更长；不能以 token 降低承诺提速。
5. **还未覆盖真实项目泛化和组合版本。** 现有三项是小型合成任务；需要确认需要语义判断的源码任务不会被不恰当地合并，还要验证与主工作树已有执行统计改动的组合。未证明之前不合并、不交付。

后续应先优化默认展示对简单阅读任务的固定成本与可读性，并在相同语义下验证模型是否确实减少不必要的数据回传；不要继续为某个 fixture 加专用规则，也不要通过隐藏错误、降低校验或自动重放来换取少轮数。

复现入口：

```text
node scripts/bench-live-tools.mjs --live --apps=baseline,pimoon --baseline=<冻结的pimoon源码> --resource-source=<只读桌面资源目录> --model=gpt-6.1-sol --thinking=low --runs=3 --scenarios=locate-edit,aggregate,conditional-edit
```

该入口只在候选分支扩展了 `baseline` 对照能力。真实模型调用需要有效订阅凭据，仍应保持隔离，并保留连接失败与不完整 usage，不能无限补样直到得到好看的数字。
