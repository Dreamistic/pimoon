## 计量口径

- **实际总 token**：供应商 usage 的 `totalTokens`，跨全部模型请求累加，包含 cacheRead；六次运行的 usage 均完整。不是独立上下文长度，也不是按价格折算的费用。
- **估算工具 token**：`o200k_base` 对每次请求的工具定义、历史工具调用、历史工具结果，以及本次输出调用的估算累加。同一段历史随请求重复输入会重复计数；不是只统计新产生的工具文本，也不能与实际总 token 混加或直接相减。
- **估算可见总 token**：请求可见载荷加可见输出；隐藏推理和加密内容不计。供应商原生工具协议等也可能与本地 JSON 序列化不同，不能代替实际 usage。
- **轮数**：模型请求次数，包含最终答复；每个任务都只有一条用户指令。
- **工具耗时**：根工具执行区间的并集，排除模型等待，不重复累加 Python 内部调用和并行工具。总墙钟耗时含初始化、模型、工具、释放与测量开销。

## 观察

1. **本轮更快，但实际总 token 更多。** pimoon 三项任务均较快，累计节省 8.785 s；实际 token 在定位修改、汇总中增加，只有批量编辑减少。不能将估算工具 token 的改善称为实际总 token 或费用下降。
2. **编排优势主要体现在历史调用/结果压缩。** 工具定义本身没有更省；条件批量编辑的工具 token 改善最大，约 38.3%。
3. **主要等待仍在模型。** 记录的模型耗时合计为 o-pi 86.074 s、pimoon 76.879 s；工具并集均不足 1 s。模型事件耗时与墙钟边界不完全相同，不作精确可加分解。
4. **工具本身没有更快的证据。** pimoon 三项工具耗时均略高，累计多 142.5 ms；初始化、Python 桥接、调用内容和缓存均可能影响这个小样本，不能据此归因某个实现。
5. **有可恢复错误。** 汇总任务两边均触发预期缺失文件错误；批量编辑中 pimoon 的 edit 被“先读取再编辑”守卫拒绝一次，并导致外层 execute 报错，后续恢复成功。事件计数中的两条错误不是两次独立失败。本次未修改相关实现。
6. **仅供冒烟比较。** 每任务每应用仅一次，无重复分布或显著性结论；网络、服务端缓存与模型随机性均有影响。可优先将条件批量编辑扩为每边三次，观察实际 usage 与守卫错误是否稳定复现，而非直接扩大全量任务。

## 实际总 token 增长追查

本节仅离线分析同一批 usage 和转录，没有新增付费模型请求。核对的 `native-instructions.ts`、`session.ts`、`token-accounting.ts` 与运行 manifest 中的哈希一致。

### 1. 增长发生在输入，不是思考输出或缓存重复计数

| usage 合计 | o-pi | pimoon | 差值 |
| --- | ---: | ---: | ---: |
| 非缓存输入 | 11,879 | 14,136 | +2,257 |
| 缓存读取输入 | 10,368 | 10,368 | 0 |
| 输出（已含推理 token） | 1,449 | 1,414 | -35 |
| 总计 | 23,696 | 25,918 | +2,222 |

Pi SDK 的 `openai-responses-shared.js` 从供应商 `input_tokens` 扣除缓存得到 `usage.input`，`usage.totalTokens` 直接采用供应商 `total_tokens`。本批每次请求均满足 `input + cacheRead + cacheWrite + output = totalTokens`，没有重复加缓存。缓存可能影响价格和延迟，但不能把缓存命中当作总 token 消失。

### 2. 每轮基础输入更贵，减少轮数仍没完全抵消

没有工具历史的首轮，实际输入为：

| 任务 | o-pi | pimoon | 差值 |
| --- | ---: | ---: | ---: |
| 定位修改 | 917 | 1,404 | +487 |
| 发票汇总 | 936 | 1,423 | +487 |
| 条件批量编辑 | 943 | 1,430 | +487 |

三项差值完全一致，是本批固定协议/说明开销增加的直接证据，而不是任务内容变多。`execute` 虽然只有一个声明，但其 description 包含 Python 执行规则和六个内部文件函数的目录，并非只有一个简短工具名。`src/pimoon/codeact/native-instructions.ts` 的规则本身按 `o200k_base` 就有 418 token；`session.ts` 的 `prepareLoadout` 将这些规则和 `functionCatalog(...)` 一起放进每轮声明。当前只有六个文件工具，目录压缩带来的收益不足以轻易摊平执行环境规则。

418 是本地文本计数，487 是供应商首轮输入差，不能断言 487 全由该段规则造成；schema、函数目录和系统工具策略的差异也在内。尚未做删减规则的同条件 A/B，不把它们逐项伪装成供应商实测。

用每项任务的 `首轮实际输入 × 模型请求数` 定义“重复基线”，剩余实际输入记为“历史增量”，可以精确拆账：

| 拆分 | o-pi | pimoon | 差值 |
| --- | ---: | ---: | ---: |
| 重复基线 | 13,987 | 18,458 | +4,471 |
| 历史增量输入 | 8,260 | 6,046 | -2,214 |
| 输出 | 1,449 | 1,414 | -35 |
| 合计 | 23,696 | 25,918 | +2,222 |

这是基于首轮基线的算术分解，不是供应商提供的语义级 token 归因。直观上，pimoon 13 轮每轮多 487，增加 6,331；少跑两轮省下对应 o-pi 首轮基线 1,860，仍净增基线 4,471。历史压缩省下的 2,214 没有覆盖它。

### 3. 发票汇总没有充分利用 Python 内部计算

该任务两边都是四轮，但 pimoon 总量多 2,060。上述拆账中，重复基线多 1,948、历史增量多 184、输出少 72，正好对应增长量。

转录显示 pimoon 的执行过程：

1. 调用 `ls` 并打印目录。
2. `batch('read', ...)` 读取 12 份发票和缺失文件，然后逐个 `print(p, r)`，把完整 `{ok,value/error}`、`<read>` 包装及转义换行全部发回模型。
3. 下一轮才在持久 Python 内存中解析 `results`、求和并写入 `summary.json`。

它还回显了带长绝对路径的缺失错误，并由 `tool_failures` 再汇报一次。根工具返回文本估算为 pimoon 874、o-pi 534 token，前者多 340。若留在同一个 Python 块中检查批量结果、计算并写入，只返回汇总和缺失状态，就有机会同时压缩回传内容和减少一轮；这是优化候选，并非已验证的收益。

因此汇总任务当前既没有轮数优势，也没有历史输入优势。批量编辑则相反，历史增量少了 2,228，最终仍省 714 token；定位修改只省 170 历史增量，不足抵消基线。

### 4. 为什么估算工具 token 明明下降，实际却增加

`token-accounting.ts` 用本地 tokenizer 计量 JSON 序列化后的请求；供应商并不保证把请求元数据逐字作为模型文本分词。尤其历史 `function_call` / `function_call_output` 携带 `id`、`call_id` 等字段，o-pi 的独立调用多，本地 JSON 开销更大。SDK 在 `convertResponsesMessages` 中生成这些协议项，但它们在供应商内部究竟占多少 token 无法从客户端 JSON 得出。

本批**估算输入与实际输入（含缓存）的差距**：

| 应用 | 本地估算输入 | 实际输入 | 估算高出 |
| --- | ---: | ---: | ---: |
| o-pi | 35,334 | 22,247 | 13,087 |
| pimoon | 26,840 | 24,504 | 2,336 |

差距明显不对称。因此“估算工具 token -24.2%”只能说明可见序列化载荷的估算改善，不能作为实际模型 token 节省比例。历史压缩的方向有实际输入拆账支持，但其节省规模没有本地 JSON 估算表现得那么大。

### 后续优先级

1. 先改善批量任务：读取、解析、汇总与新文件写入尽量在同块完成，只向模型返回决策所需摘要，避免 `print` 整个 batch 结果。
2. 精简原生执行规则，按本次实际启用函数过滤低频说明；保留权限、取消、错误和写入限制，不为节省 token 移除安全边界。
3. 估算指标明确标为可见载荷估算，实际总量以完整供应商 usage 为准。用原任务复测才能确认真实收益；本次只追查并补充报告，不改变运行时行为。
